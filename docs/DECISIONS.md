# Decisions

A dated log of project decisions. Add new entries at the bottom, and don't rewrite old ones. If a decision is reversed, add a new entry that refers back to the old one.

| Date | Decision | Reason |
|------|----------|--------|
| 2026-10-06 | All CSV processing happens client-side in the browser; no financial data is uploaded or stored on the server. | Protects user privacy and removes the need for a backend. |
| 2026-10-06 | Host as static files on Namecheap Stellar shared hosting (cPanel). | Hosting is already paid for, and static files keep running costs near zero. |
| 2026-10-06 | SSL via Let's Encrypt using acme.sh on the server. | Free, automated certificate renewal that works on cPanel shared hosting. |
| 2026-10-06 | Deploys go to a staging subdomain first, then production. | Catches broken builds before real users see them. |
| 2026-10-06 | Real bank exports live in `~/finance-data/`, outside the repo, and Claude Code is denied read access to that folder. | Keeps real financial data out of git and away from AI tooling. Only anonymized fixtures go in `tests/fixtures/`. |
| 2026-10-07 | acme.sh manages certificates for all five names, including staging. The Namecheap SSL plugin is retired: "HTTPS by default" is switched off, and acme.sh's deploy replaces the plugin's staging cert (the plugin can't release staging). | One renewal system avoids two tools overwriting each other's certificates. |
| 2026-10-07 | First certificate issued with DNS validation using a short-lived cPanel API token; renewals use webroot validation, and the token was removed and revoked. | A server-level HTTP-to-HTTPS redirect blocks webroot validation for names without a cert yet. Keeping a full-access token on the server permanently would turn a website compromise into an account takeover. |
| 2026-10-07 | v1 covers a single account: the one the user's direct deposit goes into. It shows monthly cash flow and spending by category. Transfer detection between accounts is deferred past v1. | One account holds both income and most spending, so it delivers the core value without the hardest problem. |
| 2026-10-07 | v1 fixtures and format support start with Regions, then Wilson Bank & Trust. | These are the banks the first users (owner and family) actually use; two formats keep column mapping small while preventing a one-bank design. |
| 2026-10-07 | Categories are assigned in this order: the user's own rules, then the bank's category column if present (mapped onto our standard category set), then built-in starter rules, then uncategorized. Tagging a transaction creates a remembered rule. | Most rows are categorized on first drop with no AI and no network; user intent always wins. |
| 2026-10-07 | Transactions persist in the browser (IndexedDB) so history builds up between visits. A "Forget my data" control wipes everything. Amends the storage wording in PRODUCT.md principle 1. | Trends need months of history; re-dropping files every visit is too much friction. Data still never leaves the device. |
| 2026-10-07 | Users can export their full state (transactions, category rules, column mappings) to a versioned file and re-import it. Re-importing merges with existing data using the normal duplicate logic. | Browsers can clear storage on their own. The export is the durable record and also covers backup, device moves, and growing the history window. |
| 2026-10-07 | The month is the unit the app stores and reports on. Files are split into the months they cover. Duplicates are handled by date coverage per account: rows are added only for dates not already held. Partial months are flagged in the UI. Quarter and year views are roll-ups of months. | Bank exports are usually ~90 days and overlap; date-level coverage avoids double counting without wrongly merging genuine same-day twin transactions. |
| 2026-10-07 | Imports have no size cap and must handle multi-year files without freezing the UI. Any retention or trimming happens after import, not before. | Re-imported exports grow without limit, and the app must read a file to know what's in it. |
| 2026-10-07 | The finance helper lives at trend-drift.com/finance. The root is reserved for a future platform landing page. Each tool namespaces its browser storage keys. | Keeps one certificate (subdomains would need new cert names via DNS issuance) and leaves room for more tools; path-based tools share one storage origin. |
| 2026-10-07 | v1 makes no network requests after loading. This is enforced with a strict Content Security Policy that blocks outbound connections, and all assets (fonts, scripts) are self-hosted. A future opt-in AI categorization tier is the only planned exception. | Turns the privacy promise into a browser-enforced guarantee, including against misbehaving dependencies. |
| 2026-10-07 | No analytics in v1. | Keeps the privacy promise airtight and avoids running costs. |
| 2026-10-07 | Long-term vision is three tiers of capability, with AI categorization at the top. v1 is the first tier. Pricing is deferred until tiers have defined features. | Lets v1 stay simple while not blocking later growth; AI is where real running costs appear. |
| 2026-10-07 | Parsing, categorization, duplicate handling, and month roll-ups live in plain modules with no React dependency, tested against fixtures. | Makes the hard logic testable, keeps the chart library swappable, and lets future tools reuse it. |
| 2026-10-07 | Desktop-first; the app must be functional, not polished, on phones. | Getting a CSV from a bank is a computer task; phones are for glancing at results. |
| 2026-10-07 | v1 includes a "Try with sample data" button, built from the synthetic test fixtures. | Shows the payoff before asking users to go find their bank exports. |
| 2026-10-07 | Bank CSV imports never include transactions dated on the day of import (the user's local date). A file dropped on 2026-10-07 skips every 2026-10-07 row; that day is picked up from a later export. | The current day may be incomplete or still pending. Combined with date-coverage merging, a partial day would otherwise block the complete version forever. |
